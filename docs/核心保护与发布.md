# SafeCleanerPro 核心保护与发布

本次已完成的构建、校验结果与快照范围见
[2026-10-17 验证记录](保护验证记录_2026-10-17.md)。

## 保护的范围

本次实现提高离线版本的分析与篡改成本，不承诺“不可逆向”。某个竞争产品的
规则库暂未被解密，只说明当次研究没有成功；RAE 等工具仍可能通过反汇编、
调试、进程内存、函数调用观察获得逻辑或规则。不能把程序必须使用的解密密钥
永久藏在同一个离线客户端里。

现在采用：

1. **原生编译**：正式入口使用 Nuitka standalone，把清理、迁移、去重、规则
   适配与授权校验模块编译；没有普通 PyInstaller 的 Python 字节码分发路径。
   核心里的字符串和数据仍可能被分析，原生编译不是强制保密保证。
2. **加密规则**：`client_app/rules_library.json` 与
   `client_app/rules/trace_rules.json` 经结构检查、压缩、AES-256-GCM 加密成为
   `rules.scpack`，每次构建生成新密钥和随机 nonce。自有的 Python 规则表随模块
   编译；本次未把第三方规则变成自有资产。
3. **发布者签名**：独立 Ed25519 私钥签名整个规则包；公钥、包摘要、构建编号
   编译进程序。摘要绑定这次构建，签名证明规则包来自对应发布者。修改摘要
   无法替代发布者签名。替换成另一版本的规则包同样失败。
4. **启动先校验**：在载入主界面、扫描、删除前验证规则包。缺失、损坏、错版
   都停止；没有读取旁边明文 JSON、工作目录规则或关闭校验的环境变量开关。
   规则明文仅作为运行时 Python 对象存在，没有临时明文规则文件。
5. **发布检查**：只复制明确列出的生产模块与图片；拒绝 `.py/.pyc/.pdb`、私钥、
   明文规则出现在发行目录；对原生 EXE 跑自检，成功后才生成交付 ZIP。
   构建失败不会自动降级，也不会覆盖 `client_app/latest` 的旧程序。
   构建前还检查本地模块依赖：新增 `rules_extra.py` 等模块而未纳入保护流程时，
   直接停止，避免宽泛异常捕获导致发行版悄悄漏规则。

源码开发仍使用明文输入文件，方便审阅和新增规则；任何 frozen/compiled 版本
必须使用规则包，旧 spec 的普通打包版本不再是受支持的正式发布方式。

## 一次性准备（项目根目录，PowerShell）

```powershell
python -m venv .venv-release
.venv-release\Scripts\python.exe -m pip install -r tools\requirements-release.txt
.venv-release\Scripts\python.exe tools\build_release.py init-key
```

签名私钥存放在
`%LOCALAPPDATA%\SafeCleanerPro\release-signing\signing-key.dpapi`，使用 Windows
当前用户 DPAPI 加密，和旧授权 RSA 密钥完全独立。初始化采用独占创建，不会
覆盖既有发布密钥。构建阶段只在内存解开签名私钥。

DPAPI 文件依赖原 Windows 用户的解密凭据，复制该文件到另一台电脑不能当作
可移植备份。换构建机需另行设计密钥迁移/托管；当前可以初始化新密钥生成新的
完整程序版本，既有离线版本不依赖这台机器继续运行。

## 每次发布

```powershell
.venv-release\Scripts\python.exe -m unittest discover -s tests -v
client_app\build.bat
```

输出在 `build/protected/<构建编号>/`：

- `SafeCleanerPro-protected.zip`：编译、自检和发行目录审查全部通过后才生成。
  用户解压整个目录后运行 `SafeCleanerPro.exe`，不能仅取 EXE。
- `build-info.json`：本次代码/规则/EXE 摘要、发布者公钥指纹、自检状态。
- `compilation-report.xml`：编译器报告，留给开发者审查。
- `stage/`、`native/`：开发者构建材料，含源码、生成的 AES 配置和 C 代码；
  不能作为发行包提供，也不要推到公共仓库。

本次选择 standalone 便于审查和测试。压成单文件不会自然增加安全性。
首次原生编译会下载 Nuitka 所需的 MinGW 工具链，后续复用缓存。构建依赖应在
独立虚拟环境维护；编译报告记录版本，升级后重新执行发布验收。

只想检查规则打包，不编译程序：

```powershell
.venv-release\Scripts\python.exe tools\build_release.py prepare
```

`prepare` 产物明确标注 prepared-only，不是可分发程序。

## 后续新增规则

请复制 [规则接入 AI 指令](规则接入_AI指令.md) 给其他 AI，并附上具体规则来源。
自有常规清理项继续放 `client_app/cleaner_rules.py`；深度缓存规则放
`client_app/deep_cache.py`。无需修改加密层，重新构建即可。

外部库继续维护 `client_app/rules_library.json` 的 `winapp2/dismpp/sources`
结构；痕迹库使用 `client_app/rules/trace_rules.json` 的组/条目结构。仓库根目录
`rules/` 是研究材料目录，不是正式入口。不要只修改研究副本就宣称产品已接入。

当前包与程序严格绑定。更新一条规则也必须重新发布整包；这里没有实现在线规则
热更新、防跨版本回滚存储、在线密钥服务或证书签名。后续若做热更新，要另设
版本策略与可信公钥轮换，不能简单放开本次的摘要绑定。

## 现有权利与后续方向

仓库当前 `LICENSE` 为 MIT，允许相应的使用和复制；本次没有修改它。
已经公开的源码不能通过加密发行包重新变成秘密。上游规则的来源和已有许可
记录在 [THIRD_PARTY_RULES.md](THIRD_PARTY_RULES.md)，随发行包保留。

更高成本的下一层是把未来独有的判定服务、规则生成流程留在服务端，并评估
商业代码保护与 Authenticode 发布证书；本次未伪装实现这些能力。当前私钥用于
规则包签名，不是 Windows EXE 的 Authenticode 签名，也不能阻止攻击者补丁修改
整份程序或控制进程后读取解密规则。

实现依据：[Nuitka 官方手册](https://nuitka.net/user-documentation/user-manual.html)、
[AES-GCM](https://cryptography.io/en/latest/hazmat/primitives/aead/)、
[Ed25519](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/ed25519/)。
